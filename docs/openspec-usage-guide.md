# OpenSpec SDD 实操指令手册

本文档列出 HoverWord 开发过程中各场景对应的 Claude 指令，确保每次交互都有明确的流程入口和产出。

***

## 可用 Slash 指令速查

只有以下 6 个 `/opsx:` 指令是真实存在的，不要使用不存在的指令：

| 指令 | 用途 |
|------|------|
| `/opsx:propose` | 提出新变更（产出 proposal / specs / design / tasks） |
| `/opsx:apply` | 按 tasks 逐项实现 |
| `/opsx:update` | 更新已有 change 的需求或方案 |
| `/opsx:sync` | 将 delta specs 同步到主 specs |
| `/opsx:archive` | 归档已完成的 change |
| `/opsx:explore` | 进入探索模式，调研分析 |

**状态查询**不需要 slash 指令，直接用自然语言问即可（如"目前有哪些活跃的 change？"）。

***

## 0. 恢复上下文（每次新会话第一步）

```
上次到哪了
```

**触发行为：** Claude 会查看 openspec changes 状态、tasks 完成度、代码现状，给出进度摘要。

**补充：** 如果有多个 change 活跃，可追问"帮我列出所有 change 的状态"。

***

## 1. 新增需求

### 1.1 全新功能（影响 > 3 个文件）

```
/opsx:propose <功能简述>
```

**示例：**

```
/opsx:propose 添加单词发音快捷键，空格键切换发音播放/暂停
```

**产出：** proposal → specs → design → tasks，全部在 `openspec/changes/<change-name>/` 下。

**后续流程：**

```
/opsx:apply          # 按 tasks 逐项实现
/opsx:sync           # 实现完成后，同步 delta specs 到主 specs
/opsx:archive        # 归档 change
```

### 1.2 小改动（≤ 3 个文件，如调一个常量、改一段文案）

直接描述需求即可，无需走 change 流程：

```
把悬浮窗默认宽度改为 320px
```

**原则：** 如果改着改着发现影响范围扩大了，停下来，改用 `/opsx:propose` 走正式流程。

***

## 2. 需求变更（已归档或进行中的 change 需要调整）

### 2.1 进行中的 change 需要改需求

```
/opsx:update <change-name> <变更描述>
```

**示例：**

```
/opsx:update mvp-v0-1 右键菜单增加"导出收藏"选项
```

**产出：** 更新 proposal / specs / design / tasks，保持 artifacts 间一致。

### 2.2 已归档 change 的需求要改

先确认要改什么，再决定方式：

```
之前归档的 feat01 里，窗口最小宽度想改成 250px，
这需要新建一个 change 还是直接改代码？
```

**Claude 会判断：**

- 小范围调整 → 直接改代码 + 更新主 specs
- 大范围变更 → 建议新建 change（如 `feat02-*`），走 `/opsx:propose`

***

## 3. 实现任务

### 3.1 开始实现一个 change

```
/opsx:apply
```

**行为：** Claude 读取 tasks.md，从未完成的第一个 task 开始实现。每完成一个 task 会更新 tasks.md 中的 `[ ]` → `[x]`。

### 3.2 只实现特定 task

```
/opsx:apply 只做 task 3.2 到 3.5
```

### 3.3 实现中途暂停，下次继续

直接关闭会话即可。下次说"上次到哪了"，Claude 会从 tasks.md 中未完成的 task 继续。

***

## 4. 人工验证

### 4.1 实现完成后，请求全面验证

```
帮我对照 spec 逐项验证当前实现，列出所有不符合 spec 的地方
```

**或更具体：**

```
对照 floating-window spec 验证悬浮窗的所有 scenario
```

**产出：** 逐 scenario 对比报告，标注 ✅ 通过 / ❌ 不符 / ⚠️ 部分符合。

### 4.2 构建 + 运行测试

```
构建并运行所有测试
```

**产出：** xcodebuild 编译 + XCTest 执行结果。

### 4.3 运行 app 看效果

```
重新运行
```

**产出：** 杀掉旧进程 → 构建 → 启动新 build。

***

## 5. 验证发现问题需要修复

### 5.1 实现与 spec 不符（Bug）

**先报 bug，再修复：**

```
发现以下问题，请修复：
1. 悬浮窗最小宽度应该是 200px，实际是 600px
2. 右键菜单位置偏右，离鼠标太远
```

**Claude 的行为应该是：**

1. 读取 spec 确认正确行为
2. 定位代码中的偏差
3. 列出修复计划（影响 > 3 个文件时）
4. 修复
5. 构建 + 测试验证

### 5.2 Spec 自身有矛盾或不可实现

```
Spec 里写的 .liquid 材质在当前 SDK 不存在，
帮我更新 spec 并修复实现
```

**Claude 的行为：**

1. 确认矛盾点
2. 提出 spec 修改方案（2-3 个选项 + 权衡）
3. 你确认后，更新 spec + 代码

### 5.3 修复后需要补记录

如果修复了 bug 但没有走 change 流程，建议在下一个 change 归档前，口头补记：

```
刚才修复的 Constants 数值问题，记到 feat01 的 tasks.md 里作为补充 task
```

***

## 6. Spec 同步

### 6.1 把 change 的 delta specs 同步到主 specs

```
/opsx:sync
```

**行为：** 读取当前活跃 change 的 delta specs，与主 specs（`openspec/specs/`）对比，智能合并。

**何时做：** 实现完成、验证通过后，归档之前。

***

## 7. 归档

### 7.1 归档已完成的 change

```
/opsx:archive
```

**行为：**

1. 检查 artifact 完成度
2. 检查 task 完成度
3. 评估 delta spec 是否需要同步
4. 移动到 `openspec/changes/archive/YYYY-MM-DD-<name>/`

### 7.2 归档特定 change（多个活跃 change 时）

```
/opsx:archive feat01-float-window-enhancements
```

***

## 8. 探索 / 调研（不确定需求时的前置环节）

### 8.1 探索技术可行性

```
/opsx:explore
Liquid Glass 效果在 macOS 12-14 上有哪些可用的实现方案？
```

**行为：** 进入探索模式，不产出代码或 artifacts，只做调研和分析。

### 8.2 对比多种实现方案

```
帮我对比悬浮窗缩放的两种方案：
A. 用 NSPanel 的 .resizable styleMask
B. 手动监听边缘拖拽事件
各自的优缺点是什么？
```

**产出：** 对比表格 + 推荐方案。

***

## 9. 状态查询

> **注意：** 没有 `/opsx:status` 或 `/opsx:show` 指令。状态查询用自然语言即可。

### 9.1 查看当前所有 change 状态

自然语言提问：

```
目前有哪些活跃的 change？各自进度如何？
```

**或直接用 CLI（终端中）：**

```bash
openspec list
```

### 9.2 查看某个 change 的详情

```
帮我看看 mvp-v0-1 的 tasks 完成情况
```

**或直接用 CLI：**

```bash
openspec view
```

### 9.3 查看 spec 内容

```
帮我读一下 floating-window 的 spec
```

***

## 10. 推荐的完整开发 Loop

```
┌─────────────────────────────────────────────────────┐
│ 1. 探索需求（可选）                                    │
│    /opsx:explore                                     │
├─────────────────────────────────────────────────────┤
│ 2. 提出变更                                          │
│    /opsx:propose <需求描述>                            │
│    → 产出：proposal / specs / design / tasks          │
├─────────────────────────────────────────────────────┤
│ 3. 确认方案（人工 review）                              │
│    "帮我读一下 design.md，我看看方案是否合理"              │
├─────────────────────────────────────────────────────┤
│ 4. 实现                                              │
│    /opsx:apply                                       │
│    → 逐 task 实现，自动更新 tasks.md                    │
├─────────────────────────────────────────────────────┤
│ 5. 验证                                              │
│    "构建并运行测试"                                     │
│    "对照 spec 逐项验证"                                 │
│    "重新运行 app 看效果"                                │
├─────────────────────────────────────────────────────┤
│ 6. 修复验证发现的问题                                   │
│    "发现以下问题，请修复：..."                            │
│    → 回到步骤 5 重新验证                                │
├─────────────────────────────────────────────────────┤
│ 7. 同步 specs                                        │
│    /opsx:sync                                        │
├─────────────────────────────────────────────────────┤
│ 8. 归档                                              │
│    /opsx:archive                                     │
│    → change 移入 archive/                             │
└─────────────────────────────────────────────────────┘
```

***

## 11. 注意事项

| 规则                     | 说明                      |
| ---------------------- | ----------------------- |
| **影响 > 3 个文件的改动**      | 必须先列计划，得到确认后再执行         |
| **不确定的需求**             | 停下来问，不要自己猜              |
| **多种实现方案**             | 列出 2-3 个选项 + 权衡，不要自行决定  |
| **发现潜在 bug**           | 可以提出，但不要自行修改（除非明确要求）    |
| **每完成一个有意义的改动**        | 自动运行测试验证无回归             |
| **tasks.md 的 \[x] 含义** | 应该是"实现 + 验证通过"，不是"代码写了" |
